# 05 · 数据文件格式 (`.codeLocator`)

> 本文聚焦 IDE 本机生成的 `.codeLocator` 二进制容器，以及与 SDK 广播返回 payload 的差异。
> 设计代码：`model/CodeLocatorInfo.java`、`utils/CodeLocatorFileParser.java`。

---

## 1. 两种载荷，不要混淆

| 载体 | 内容 | 编码 | 出处 |
|------|------|------|------|
| **broadcast 传输 payload** | `BaseResponse` 子类 JSON（`ApplicationResponse` / `FileResponse` 等） | `Base64( GZIP( UTF8 JSON ) )` | 设备端 SDK `CodeLocatorReceiver.sendResult` |
| **`.codeLocator` 历史文件** | `WApplication` JSON + 截图 PNG | 自定义二进制（DataOutputStream，4 字节长度前缀） | IDE 端 `CodeLocatorInfo.toBytes` |

反向 skill 已有的 `parse-codelocator-file.ts` 解析的是后者，不要拿它去解析 broadcast 的 `FP:<path>` 文件。

---

## 2. 二进制布局（与 `~/.claude/skills/codelocator/references/02-codeLocator-file-format.md` 对齐）

`CodeLocatorInfo.toBytes` (`model/CodeLocatorInfo.java:50-77`)：

```text
+----------------+------------------------------------------------+
| 4 字节         | tagLength (int32 big-endian, Java DataOutput)  |
+----------------+------------------------------------------------+
| tagLength 字节 | "CodeLocator" (UTF-8 固定字面量)               |
+----------------+------------------------------------------------+
| 4 字节         | versionLength                                  |
+----------------+------------------------------------------------+
| versionLength  | 插件版本号 UTF-8，例: "2.0.8"                  |
+----------------+------------------------------------------------+
| 4 字节         | applicationJsonLength                          |
+----------------+------------------------------------------------+
| ...            | WApplication 的 Gson JSON (UTF-8)              |
+----------------+------------------------------------------------+
| 剩余全部       | PNG 截图 (ImageIO.write(_, "PNG", out))        |
+----------------+------------------------------------------------+
```

读取逻辑 `fromCodeLocatorInfo` (`model/CodeLocatorInfo.java:80-126`)：
1. 读 4 字节得到 tagLength，再读相应字节，必须 `"CodeLocator"`，否则返回 null。
2. 读 versionLength 跟版本字符串（不做校验，留作向后兼容）。
3. 读 applicationJsonLength 跟 JSON，`Gson.fromJson` → `WApplication`。
4. 剩余字节 `ImageIO.read` → `BufferedImage`。
5. `application == null || image == null` 时返回 null。

> 解析端不需要 GZIP，不需要 Base64；只要按 4 字节 big-endian int 切片即可。
>
> Node.js 端：`buf.readUInt32BE(offset)` 直接读出每段长度；写入端用 `buf.writeUInt32BE(len, offset)`。

## 3. 关键工具类

| 入口 | 作用 |
|------|------|
| `CodeLocatorInfo.toBytes()` | 序列化历史文件 |
| `CodeLocatorInfo.fromCodeLocatorInfo(byte[])` | 反序列化历史文件 |
| `utils/CodeLocatorFileParser.java::parseAndExport` | 把 `.codeLocator` 拆成 `<name>.json` + `<name>.png` |
| `utils/CodeLocatorFileParser.java::main` | 命令行入口（`java CodeLocatorFileParser <文件> <outDir>`） |
| `utils/DataUtils.restoreAllStructInfo` | JSON 反序列化后重建父子指针、活动指针 |

历史文件写入入口：

- `panels/ScreenPanel.java:826-828`：每次 grab 成功且非 Window 模式自动落盘
- `action/SaveWindowAction.kt`：用户手动 "另存为" 时落盘
- `action/ShowGrabHistoryAction.kt:69-87`：`saveCodeLocatorHistory` 内做容量裁剪

文件命名（`ShowGrabHistoryAction.kt:51-56`）：

```
~/.codeLocator_main/historyFile/<packageName><yyyy_MM_dd_HH_mm_ss>.codeLocator
```

> 注意：包名后**没有分隔符**直接跟时间戳，所以包名结尾是数字时容易和年份连在一起。skill 现在的 `parse-codelocator-file.ts` 在解析时应当用文件后缀 + 长度而非命名规则定位。

## 5. 跨版本兼容性

`CodeLocatorInfo.toBytes` 把当前插件版本写进文件，但 `fromCodeLocatorInfo` 不做校验。已知兼容点：

- **plugin 升级后老文件能读**：✅ 因为只 readInt + 字节流，长度自描述。
- **plugin 降级**：⚠ 如果新版引入了 `WApplication` 上的新字段，老插件 Gson 反序列化时会**忽略未知字段**（默认行为），可读但可能丢信息。
- **SDK 升级引入新 `EditType`**：✅ 不影响历史文件，只影响在线 EditView 行为。
- **PNG 编码器变更**：✅ ImageIO `"PNG"` 跨 JDK 兼容。
- **tag 字符串**：固定 `"CodeLocator"`，任何版本都不变。

> 因此：反向 skill 解析 `.codeLocator` 只要保住 "tag check + 4 字节长度切片 + JSON 反序列化 + PNG 解码" 四步即可，无需做版本分支。

## 6. broadcast 返回 payload 解码（对比）

设备端 `sendResult` (`CodeLocatorReceiver.java:493-542`) 的回执有两种形态：

### 6.1 直传（小数据）

```text
result data="<Base64( GZIP(BaseResponse JSON) )>"
```

解码：

```bash
echo '<base64>' | base64 -d | gunzip | jq .
```

### 6.2 文件落盘（大数据 / API 30+ / `KEY_SAVE_TO_FILE=true`）

```text
result data="FP:<absolute path on device>"
```

解码：

```bash
adb pull <path> /tmp/payload.txt
base64 -d /tmp/payload.txt | gunzip | jq .
```

JSON 顶层是 `BaseResponse`：

```json
{
  "code": 0,
  "msg": null,
  "obj": null,
  "data": {
    /* 例如 WApplication，或 WFile，或 String，由对应 Response 类型决定 */
  }
}
```

`code != 0` 或 `msg != null` 表示设备端报错；`msg` 取值对照 `CodeLocatorConstants.Error.*`（`no_current_activity / view_not_found / args_empty / not_ui_thread / error_with_stack_trace` 等）。

## 7. 反向操作时需要重建的"派生信息"

历史 `.codeLocator` 文件里的 JSON 是"扁平"的：View 的父子关系、Fragment 与 Activity 的反向指针、当前 Activity 引用等都没有直接序列化，反序列化后插件调 `DataUtils.restoreAllStructInfo` 重建。

反向 skill 如果直接消费 broadcast 返回的 JSON（不经 IDE），同样需要做一次 "restore"：

| 重建 | 关系 |
|------|------|
| `WView.parent` / `WView.activity` | 从 `WApplication.activity.decorViews[*]` 深度遍历 `children` 时回填 |
| `WFragment.activity` | 在 `WActivity.fragments` 遍历时回填 |
| `WApplication.activity.application` | 反向指针 |
| `WFile.parent` | 文件树同上 |
| `WActivity.startInfo` | 已经在 JSON 里 |

如果 skill 只需要 "拿数据 + 解析"，不需要重建 parent 也能用——但任何需要 "由 child 找 parent" 的高阶操作（例如 ViewLink 协议、点击链路反查）都要做重建。

## 8. 已澄清事项

- **`CodeLocatorFileParser.parseAndExport` 输出 JSON 不做字段名替换**：用 `GsonUtils.formatJson` 美化但保留 `@SerializedName` 短名，skill 端读还是要自己做映射。
- **`CODELOCATOR_VERSION` 来源是 `AutoUpdateUtils.getCurrentPluginVersion()`**：每次插件 build 后可能不同；旧文件里写的是当时的版本号，反向 skill 不要依赖具体版本字符串。
